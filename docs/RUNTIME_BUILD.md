# Construction des runtimes

Le lanceur macOS arm64 utilise des origines immuables : les archives officielles OpenWoW 0.1.2 et Ollama 0.33.2 vérifiées par SHA-256, le fork serveur Playerbots, le module Playerbots et `mod-ollama-chat` à des commits exacts. MySQL est référencé par digest multiarchitecture. Les images serveur joueur contiennent le module de dialogue désactivé afin de permettre son activation ultérieure sans reconstruire le royaume ; l’archive Ollama et le modèle ne sont téléchargés qu’après confirmation. Le chemin source de développement ne clone encore le module que si l’option est choisie pendant l’installation initiale.

Le build source local actuel est un chemin de qualification, pas le parcours joueur cible. Les releases RealmBox doivent télécharger par digest des images multiarchitecture produites une seule fois par la CI à partir des mêmes commits épinglés. Les quatre variables de compilation `REALMBOX_AUTH_SERVER_IMAGE`, `REALMBOX_WORLD_SERVER_IMAGE`, `REALMBOX_DB_IMPORT_IMAGE` et `REALMBOX_TOOLS_IMAGE` doivent toutes contenir une référence GHCR immuable `@sha256:`. Si elles sont présentes, le lanceur génère un Compose sans build et télécharge les images. Si elles sont toutes absentes, il conserve le build source de développement. Un ensemble partiel ou un tag flottant fait échouer la construction du parcours au lieu de revenir silencieusement à une provenance plus faible.

Le workflow est présent et produit le fichier de verrouillage attendu. Lors d’une publication, il refuse de produire les bundles joueur si les images ne sont pas publiquement téléchargeables, puis construit macOS arm64 et Windows x64 avec les quatre digests injectés. Aucune image n’est encore déclarée publiée : les bundles locaux courants conservent donc provisoirement le build source au lieu d’inventer une référence de registre.

Les outils AzerothCore extraient `dbc`, `maps`, `vmaps` et `mmaps` depuis le dossier `Data` du joueur monté en lecture seule. Ces outils peuvent être précompilés ; les données et les sorties d'extraction restent locales et n'entrent jamais dans une image distribuée.

Les commandes `xtask build-*` historiques restent des garde-fous de développement et ne constituent pas le chemin d'installation du produit.
